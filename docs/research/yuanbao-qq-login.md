## 结论

本次本机实验中，QQ 密码登录取得的**元宝 Cookie**可以用于现有视频号解析流程；关闭并重新打开浏览器后，登录态仍可复用。早先的可视实验仅验证可行性；后续已集成浏览器自动登录、每日 Cookie 维护与 QQ 邮箱告警，操作见[部署指南](../resolver-deployment.md)。

## 已集成的维护方案

1. [`maintain_cookie.py`](../../server/maintain_cookie.py) 在部署后立即、之后每天验证已有 Cookie；验证成功就直接复用，不启动浏览器。
2. 解析失败后用元宝 `GET /api/getuserinfo` 区分明确未登录（HTTP 401）和状态不明。只有明确失效或缺失时，才以新无头 Chromium 打开专用浏览器资料，复用登录态或从私有 `config.json` 读取 QQ 账号密码登录，跳过可选手机号绑定。
3. 新 Cookie 通过完整解析检查后，复用 [`update_cookie`](../../server/update_cookie.py) 原子替换；失败保留旧文件，解析进程无需重启。
4. 异常登录失败持久化暂停密码重试，需要 `--resume` 恢复；首次维护错误尝试用独立 QQ 邮箱资料目录给自己发通知。只发送固定错误码和时间，通知失败不递归。

`LOGIN_EXPIRED_OR_UPSTREAM_CHANGED` 也可能表示上游接口变化，不能对所有解析失败都反复重新登录。服务端统一使用 `config.json`；客户端的 `runtime/resolver_config.json` 继续只配置服务地址和访问凭证。配置、浏览器资料和 Cookie 不进入 Git 或公开日志。

补充诊断还排除了一个干扰项：`localhost.ptlogin2.qq.com:4301–4309` 的连接拒绝来自本机 QQ 客户端探测，未填写凭据的页面也会出现，不能据此认定认证服务不可达。诊断现在忽略这类失败。

实现已让共享密码登录流程先等待 QQ 账号检查；明确要求额外验证时返回 `QQ_VERIFICATION_REQUIRED`，不填写或提交密码。检查超时与检查失败分别返回 `QQ_ACCOUNT_CHECK_TIMEOUT`、`QQ_ACCOUNT_CHECK_FAILED`；QQ 邮箱保留这些具体错误，不再统一掩盖为 `MAIL_LOGIN_FAILED`。独立检查输出固定阶段码、允许列表内的站点分类、布尔状态及数字回调码，不输出凭据、Cookie、查询参数、页面正文或原始响应。

修改后的阿里云直连验收：两个入口均在账号检查后以 `QQ_VERIFICATION_REQUIRED` 退出，没有进入填写密码或点击提交阶段。这验证了“无法跳过则失败”，**不表示服务器登录成功**。未安装服务、修改现有 Cookie 或私有配置、发送邮件；正式上线、长期续期与发信送达仍未验收。

## 验证码题型、程序点击与有头/无头对照（2026-10-20）

用户随后要求实际展开验证码，确认题型及程序能否完成。此前由 `CHECK 1` 直接推断“不可自动完成”证据不足；它只表示需要进入验证码流程。沿用独立临时环境，仅填写 QQ 账号、密码保持为空，通过页面原生登录按钮打开腾讯验证组件；不修改验证码判定、回调或票据，不调用第三方打码服务。

| 入口 | 实际题型与程序操作 | 结果 |
| --- | --- | --- |
| 元宝 QQ 登录 | 六宫格语义图片点选，例如选择“金色花瓶”，再点击“确定”。agent 识别验证码局部截图，Playwright 执行两次鼠标点击。 | `hasVCSuccess=true`，组件关闭，已证明这道验证码可以经程序操作完成。 |
| QQ 邮箱 QQ 登录 | 同样是六宫格语义图片点选，观察到“鸭子”“一只猫”等描述。分别点击对应图片和“确定”。 | 两次均未收到成功标志，组件继续出题；一次后续题要求选出包含指定文字的所有图片。尚不能区分前题被拒或连续挑战要求，不能声称已通过，也不能据此断言程序一定无法通过。 |

上述过程中没有人工在浏览器里选图或点击，但选图依赖本次会话中 agent 的图像理解；服务器现有 Python 登录脚本没有通用识图模块。因此“一个验证码已通过”“服务端能独立识别任意题目”“完整登录成功”是三个不同结论，本次只证实第一项的元宝样本。所有验证码探查均未填写或提交密码，也未发信、覆盖 Cookie 或安装服务。只截取验证码组件，未保存账号输入框或其他私有页面；远端截图与临时浏览器资料在退出时清理。

为核对浏览器模式，在相同阿里云、相同 QQ 邮箱入口和同一账号上，使用新临时资料做账号检查：

| 模式 | QQ 检查 | 额外状态 |
| --- | --- | --- |
| `headless=False`，由已有 Xvfb 提供虚拟显示 | `CHECK 1` | `needVc=true`、`needShowNewVc=true`，无检查超时。 |
| `headless=True` | `CHECK 1` | 相同结果。 |

因此，仅从无头切到有头，没有消除本轮阿里云直连的验证码要求。Xvfb 的有头浏览器不等同于真人桌面操作；本轮也没有无自动化控制的普通浏览器对照，尚不能排除 Playwright 特征与网络环境共同影响。模式对照只做账号检查，没有提交密码，Xvfb 随测试命令结束。

当前 `QQ_VERIFICATION_REQUIRED` 是尚未集成验证码识图处理时的保守退出行为，不是验证码必然只能由人工完成的证明。进一步接入自动识图及验证处理需要单独明确实现方式并验收；此前的账号密码完整登录目标仍未达成。

## 联网核实触发因素（2026-10-20）

用户要求搜索公开资料以确认人机验证的触发原因。本轮只采用腾讯和浏览器官方资料，未新增真实账号登录尝试。结论：**网络出口相关因素是现有对照中证据最强的影响因素；自动化或设备特征可能参与，但没有找到 QQ 对本次 `CHECK 1` 命中项的公开解释或查询入口。** 不能将这一结论进一步写成“机房 IP 一律触发”“阿里云 IP 被封”或“Playwright 是唯一原因”。

为核对自动化信号，另在阿里云锁定的 Chromium 中只加载本地测试 HTML，不访问 QQ、不读取账号密码：

| 浏览器启动模式 | `navigator.webdriver` | User-Agent 含 `HeadlessChrome` |
| --- | --- | --- |

这说明切换有头模式确实移除了本次 User-Agent 中的无头标记，但没有移除所有可见的自动化特征。它可以解释为何“改有头”不保证改变风险判定，却不能证明 QQ 使用了具体哪一个属性。本轮未修改这些属性或浏览器参数，临时资料和 Xvfb 随检查退出清理。

结合前述对照，当前因果判断如下：

- **证据最强：网络出口关联因素。** 相同云端浏览器、账号和新资料，经 Windows 出口返回 `CHECK 0`，两个云出口返回 `CHECK 1`。SSH/SOCKS 对照同时改变了源 IP、DNS/路由及出口 TCP 特征，尚不能将影响精确归到 IP 信誉或某一项。
- **可能参与：自动化及设备特征。** 两种模式均存在自动化标记，但相同 Playwright 环境经 Windows 出口仍免验证，因此自动化标记本身不足以解释全部差异；仍可能与其他风险共同作用。
- **不能作为唯一解释：无头模式、密码错误、旧 Cookie。** 有头仍要求验证；未输入密码就收到 `CHECK 1`；出口对照两边均为新的浏览器资料。账号历史、请求频率等因素仍可能参与综合判定，尚未分离。

更细的技术归因需要在同一出口下对照普通浏览器与自动化浏览器，或取得 QQ 官方对对应时间请求的风险说明。目前没有做前者，也没有找到保证提供后者的公开接口。第三方关于特定 IP 段或浏览器标记的经验不能替代本次因果证据；腾讯云控制台登录异常的规则也不能直接套用于 QQ 账号预检。
